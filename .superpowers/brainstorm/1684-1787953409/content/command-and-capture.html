Command And Capture Design

How replies in Telegram become safe OMP actions, and how the broker captures the terminal that actually ran the session.

Telegram Command Flow
1. Operator replies to a session post
2. Broker resolves bound session
3. Parser classifies message
4. Broker dispatches action to session
5. Bot posts ack or result
Terminal Capture Flow
1. Session registers terminal handle
2. Completion event reaches broker
3. Broker requests final terminal snapshot
4. Renderer composes terminal screenshot + summary
5. Telegram post includes the real terminal ending

Recognized Reply Commands

1

OMP Commands

/goal ..., /advisor ..., and plain follow-up text are transformed into structured OMP user input for that session.

2

Guarded Shell

/exec ... runs only through an allowlisted shell bridge with audit logging, sender checks, and explicit command echo in Telegram.

3

Session Control

/stop, /status, and /post remain broker-level controls tied to the replied session post.

Recommended Capture Mechanism

Use A PTY Transcript + Renderer

  • Wrap the OMP session in a managed PTY
  • Mirror terminal output into a rolling transcript buffer
  • Render the final visible rows into a terminal-style image at completion time
  • Avoid brittle desktop screenshot dependencies

Do Not Depend On OS Screenshots

  • Headless servers may not have a GUI
  • Real screen capture is harder to secure
  • Window focus and terminal emulator differences create noise

Recommended Result Post

Post one completion image that combines the assistant summary and the terminal ending, or post the existing long-photo plus a second terminal screenshot when the terminal view is materially different.
