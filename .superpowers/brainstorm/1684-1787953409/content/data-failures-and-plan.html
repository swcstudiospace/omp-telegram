Data, Failures, And Delivery Plan

The final design section: what the extension stores, how it behaves when parts fail, and how to implement it in safe slices.

Persistent Records
Session registry: session id, title, cwd, pid, heartbeat, mode, terminal handle
Post binding: Telegram channel post -> session id
Command audit: who sent what, when, parsed kind, dispatched result
Capture metadata: transcript path, terminal dimensions, rendered image path
Broker state: update offset, daemon pid, socket, locks
Failure Handling
If Telegram is down, keep broker alive and retry polling/posting
If session is offline, reply with offline status and do not drop audit
If terminal capture fails, still post completion with explicit capture-failed marker
If `/exec` is denied, reply with policy reason and log it
If reply target is missing, say it is not a bound OMP session post

Recommended Data Model Additions

A

Broker Protocol

Add message types for terminal registration, terminal snapshot requests, OMP command dispatch, guarded shell dispatch, and command acknowledgements.

B

Session Runtime

Add a terminal adapter inside each session that can mirror output into a rolling PTY transcript and execute approved routed commands.

C

Telegram Parser

Upgrade reply parsing so `/goal`, `/advisor`, `/exec`, `/stop`, `/status`, and plain text each map to distinct broker actions.

Implementation Slices

Slice 1

  • Add protocol types and broker command routing
  • Support `/goal`, `/advisor`, plain text, `/stop`, `/status` reply commands
  • Return Telegram acknowledgements for accepted and rejected commands

Slice 2

  • Add terminal adapter and rolling transcript capture
  • Render terminal-ending image from transcript
  • Post completion with terminal evidence attached

Slice 3

  • Add guarded `/exec` policy, allowlist, and auditing
  • Add failure-mode coverage and regression tests
  • Polish operator UX and docs

Test Plan

Cover parser tests for reply commands, broker routing tests for online/offline sessions, terminal transcript rendering tests, completion-post tests with fallback behavior, and integration tests for end-to-end reply-to-session control.
